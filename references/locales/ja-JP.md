## 2. 冲突裁决

**空格（全角与半角之间）**：
- JTF 基本ルール 10：「半角文字と全角文字の間に半角スペースを入れない。」
- Microsoft §4.1.11：「Between full-width and half-width characters — In principle, insert a half-width space.」
- 公用文：无规定。
- 裁决：**不是有唯一正解的问题。** 翻译/出版行业选 JTF（不加）；微软生态、软件 UI、IT 文档选 MS（加）。项目级开关 `--space jtf|ms`，全篇统一，`char_lint.py` 只报一致性。

**长音**：内閣告示「外来語の表記」注 3 原文：「英語の語末の‐er,‐or,‐arなどに当たるものは,原則としてア列の長音とし長音符号「ー」を用いて書き表す。ただし,慣用に応じて「ー」を省くことができる」，并把「コンピュータ」列为允许例。Microsoft 2008-07-25 变更 314 语改为加长音，依据即内閣告示。裁决：**「コンピュータ」不是错**，只判"全文是否统一"。

**「約」**：JTF §3.2.5 确认「半角の ~（チルダ）は使いません」；公用文「概数」条给的写法是「二十余人」「数十人」「20人余り」「40～50人」，未出现「約」。裁决：「約」是惯用不是规范，可以用，不要写成"规范要求"。

**波线**：区间号正解 U+301C WAVE DASH（jlreq 附录 A 收录；U+FF5E FULLWIDTH TILDE 是 Windows CP932 历史误映射，jlreq 中不出现）。实证：JTF 自己的官方 PDF 正文里波线用的就是 U+FF5E。裁决：印刷/文档用 U+301C；**软件字符串禁用全角波线**（Microsoft 警告会导致 build error），改「から」或半角连字符；`char_lint.py` 报 U+FF5E。

**引号**：日语用「」『』；英文材料混排时英文引号保留 " "。

## 4. 语体与敬语

敬語の指針（文化審議会 2007）五分类：尊敬語／謙譲語Ⅰ／謙譲語Ⅱ（丁重語）／丁寧語／美化語。商务文书默认丁寧語（です・ます）+ 对客户用尊敬語、对己方用謙譲語；不要三重敬语（お伺いさせていただきます 之类）。

| 材料类型 | 语体 |
|---|---|
| 投资/商务提案、社群公告、UI 消息、邮件 | です・ます |
| 学术、规范、内部技术报告、合同 | である |
| UI 菜单、按钮、标题、表格 | 体言止め |
| **スライド資料（ピッチデック・提案書）** | **体言止め主体**。です・ます は「説明が要る整文」だけ。**混在は翻訳感の主因** |
| **短通知（トースト／スナックバー）的结尾句点** | **1 文で完結する短い通知は「。」を付けない**；2 文以上、または説明・対処方法が続く場合は付ける |

敬称：个人「様」；组织「御中」；「殿」避免；「さん」口语。自称：弊社／当社（对外）、当社（中性）、私ども。

### 4a. スライド資料の語体は「役割」で決める——源文の句読点で決めてはいけない

**幻灯片是体言止め主体**，です・ます 只用于**需要说明的整句**。两者混在一起是**翻译感的主因之一**。

**分层依据必须是"这一格在幻灯片上扮演什么角色"**（見出し／ラベル／指標／説明文），
**不能照搬源文的标点分布**。

实测（某商业提案 zh→ja）：样式表把分层判据定成
「**源文该条以「。」结尾 → です・ます；无「。」→ 体言止め**」，理由是"可机械复核"——
结果三位母语者里两位指出语体混在：
「日本のスライドは**体言止め＋名詞句で統一**し、説明文が必要なときだけ「〜です」」（A）／
「前半は体言止めなのに最後2文だけ丁寧語。**統一してシャープに見せるのが基本**」（C）。

**这是"廉价对应"陷阱打在语体层**——源文的标点分布被整体搬运。
同一形状在实测中出现过三次：标点用法、中黑用法、上面这次的语体分层。
**"可机械复核"是好性质，但判据本身错了，机械复核只会把错误执行得更彻底。**

### 4b. トースト／短通知の結尾句点（出处与实测）

**规则**：単文の短い通知 → 「。」なし。複文・説明が続く → 「。」あり。

**依据**：
- 母语者 **3 人一致**（独立回答、盲测问卷 Part 2）选「付けない」，各自举 **LINE / メルカリ / PayPay** 的实际トースト为例。
  理由收敛于：「トーストは"読む"より"目に入る"もの。句点があると文章感が出て通知として重い」
  「句点を打つと機械的なシステムエラーのように見える」。
- 其中一人主动给出分界线：**「1文だけで完結する短い通知なら付けない。2文以上や、説明・対処方法まで続く文章なら付ける」**
  （例：「処理に失敗しました。もう一度お試しください。」は句点あり）。
- **与实测统计吻合**：某真实项目日语全表 —— **长正文 45/45 全部带「。」**，
  分裂全部集中在 37 条短状态句（21 带 / 16 不带）。即"长的一致、短的混乱"，正是缺这条规则导致的。

**核验程度**：母语者证言 + 我方全表统计。**未逐条截图核验各 App 的实际字符串**，
引用时按「母语者一致证言」而非「厂商规范」计。

**机检**：`char_lint.py` 会数出短状态句两侧的分裂并列出少数派（只报告不裁决）。

## 7b. 母语者会改、脚本查不出的搭配（实测积累）

以下问题类型全部来自真实项目的母语反馈（例句已改写为示意），**不是语法错误，是"日本人不这么说"**。脚本查不出，单语遍才抓得到。
每条给「日本人会怎么读」而不只给替换词，因为替换词换个语境就不对了。

### 名词搭配不成立

| 写法 | 为什么日本人会改 | 方向 |
|---|---|---|
| 「データをまとめてお持ちの方」 | 日语不说「まとめて持つ」。まとめて 修饰的是**处理动作**（まとめて処理する），不是持有状态 | 「大量にお持ちの方」，或把 まとめて 移到动作上 |
| 「〜する自動化をご利用いただけます」 | 长定语压在「自動化」这个抽象名词上，读者要读到最后才知道主词是什么（触发器 1） | 拆成「〜を自動化できます」这种动作句 |

### 组织与职种的称呼

| 写法 | 问题 | 方向 |
|---|---|---|
| 「ECチーム」 | 英文 team 直搬。日语按**职种**称呼，不按组织单位 | 「EC担当者」「ECサイト運営者」 |

### 动态字符串特有的不自然

| 写法 | 渲染后 | 问题 |
|---|---|---|
| `あと{n}必要` | あと3必要 | **数字裸着没量词**，日语读着卡。要「あと3回必要」「あと3ポイント必要」 |
| `{count}件が失敗しました` | 3件が失敗しました | 把**文件**写成失败的主体。日语说「3件のファイルの処理に失敗しました」 |
| `成功{ok}件、失敗{ng}件` | 成功3件、失敗1件 | 英文式字段倒置的**电报体**。同组别的提示是です・ます 时语气会忽高忽低 |
| `{format}に変換完了` | PDFに変換完了 | 省略过度，像**系统日志**不像给用户看的结果标题 |

**通则：动态字符串里数字后面必须有量词，主体必须是"处理/操作"而不是"物件"。**

### 选项说明的轴要齐

一组并列选项的说明必须回答**同一个问题**。实测踩过这类反例（下面是示意）：

```
ライト        個人向け         ← 用途
スタンダード  おすすめ         ← 推荐标记
プロ          高品質           ← 品质
マックス      容量最大         ← 容量
```

四行在回答四个不同的问题，读者无法横向比较。**先定轴（用途？品质？推荐？），再写四条。**

## 8. 与 char_lint.py 的对应

`python3 scripts/char_lint.py <file> --locale ja-JP --space jtf|ms [--software]`
报：U+00B7 / U+2022 → U+30FB；U+FF5E → U+301C（`--software` 时两者都报）；数字间 ASCII ~ 与 en dash；半角片假名；全角英数字；括号全半角混用；连续空格；「約」后接波线；片假名后接「一」「1」「１」（长音混淆）；CJK 旁的 ASCII 逗号句号；空格策略一致性计数。
