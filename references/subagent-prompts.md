## 1. 调用规范

- Claude Code 里用 Agent 工具，`subagent_type: general-purpose`；Codex 等其他工具里用它们等价的子 agent 能力。每个 subagent 是干净上下文，**不继承主对话**，所以提示词里必须写全：文件路径、场景、捷径、要读的包、输出格式。
- 主对话只做：拆段、派发、合并、定级、写报告。主对话不自己审。
- 双语遍按段派发（每段 ≤ 约 1500 源文字符）；段多时可并行派多个 subagent，每个带同一份 glossary 命中条目。
- **只注入该段命中的术语条目**（源语词在该段出现的），不塞整个术语表。
- 输出格式固定，主对话解析。**subagent 没返回、格式不对、或超时 → 该段记入"未审查段落"，不能当作零错误。**
- **译文栏只放能直接上线的字符串**（SKILL.md 铁律 9）。待确认占位、方案对比（A 案/B 案）、内部指针、宽度标注、处理说明，一律放进独立的「备注」列或独立清单。派发 T3 时把这条写进提示词，否则每个 subagent 会自己决定怎么标，合并出来的东西不能直接用。
- **改写不得改所指**（铁律 8）。发现源文事实有问题，记待确认，不替作者改。
- **不是翻译单元的东西不要立行**（铁律 9 后半）。「这个标签是代码拼的，没有 i18n key」「这个数存疑」——整条移进待确认清单，不要立一行然后在译文栏写说明。这是最容易漏的一种铁律 9 违反，因为那一格「本来就没有译文」。
- **开工文件与内核规则打架时按方向定**（铁律 10）。开工文件更严 → 照它做等裁决；开工文件事实过期或更松 → 照内核做并更新它。**两种都要记进待确认并在报告里写明按哪条做的**，否则独立审校遍会把你的取舍当成违规重报一遍。
- 交付前两条命令都要跑：`deliverable_check.py --target-locale <tgt> --source-locale <src>`，以及 `char_lint.py --locale <loc> --tgt-col <译文列号>`。**char_lint 不带 `--tgt-col` 会把源文列也当译文检**，误报能淹掉真问题。
- 合并完成后跑 `scripts/deliverable_check.py`，必须处理项清零才算交付。
- **主对话以实际条目数为准**，头部的「发现数」只用作校验（冒烟测试中出现过头部写 18 实际 19 条）。条目数与头部不符时按实际条目计，并在报告里注明。
- 占位符用 `{{ }}` 标出，派发前替换。**所有文件路径必须是绝对路径**（`{{skill_dir}}` 替换成本 skill 的绝对路径，即 SKILL.md §5 里给出的那个；subagent 里 `~` 不会展开，源文/译文/样式表路径同样要给绝对路径），否则 subagent 读不到包却不会报错，最后误报「无包，降级」。

## 2. 模板 A：单语遍（只读译文）

```
你是 {{目标语}} 母语读者，正在读一份 {{材料类型}}。你**看不到源文**，只看译文。

场景：{{场景一句话}}
目标 locale：{{locale}}。先读这两个文件，只读一遍：
- {{skill_dir}}/references/locales/{{locale}}.md（样式表默认值与冲突裁决）
- {{skill_dir}}/references/diagnostics.md 的第 5 节（四触发器）和第 9.11 节（不该误杀）
项目样式表（如有）：{{style-sheet 路径}}

任务：通读译文文件 {{译文路径}}，用"这像不像本地人写的"而不是"有没有错"的眼光，标出：
1. 读起来不像母语者会写的句子（生硬、翻译腔、搭配不对）
2. 四触发器命中：同形词可疑 / 说不出在哪见过的词 / 可疑的外来语音译 / 行话不像本行业的说法
3. 语体断裂（敬体常体混用、正式度忽高忽低、与场景不符）
4. 涉及钱、地位、规模、合法性的词里有负面联想的
5. 标题与其下内容性质不符的

规则：
- 不猜源文。你只报"这里读起来有问题"，不报"翻错了"。
- 每条给位置（段号 + 引用原句前 15 字）。
- 不确定的也报，但标「不确定」。宁多勿漏，后面有人复核。
- 不要改写全文，不要给整篇润色。

输出（严格按此格式）：
发现数: N
未审查段落: <段号列表 或 无>
---
A-01 【S03 / "……"】 类型：<翻译腔|同形词|出处存疑|外来语|行话|语体|褒贬|标题>  确定度：<高|中|低>
- 译文原句：
- 问题：
- 建议（可选）：
...
```

## 3. 模板 B：双语遍（逐段对照）

```
你是双语审校者，任务是对照源文找出**只有对照才能发现**的错误。译文读起来通顺不代表没错。

语对：{{src}} → {{tgt}}；目标 locale：{{locale}}
场景：{{场景一句话}}
材料类型：{{材料类型}}（{{该类型的风险重心一句话}}）
本次捷径（最要防的失败模式）：{{捷径描述}}

先读：
- {{skill_dir}}/references/pairs/{{src}}-{{tgt}}.md（语对包：假朋友、结构映射）
- {{skill_dir}}/references/diagnostics.md 第 3、4、8 节和第 9 节例子
本段命中的术语（必须按此用词，否则报术语不一致）：
{{glossary 命中条目，格式：源语词 | 目标语词 | 状态}}

本段（{{段号}}）：
<源文>
{{源文段}}
</源文>
<译文>
{{译文段}}
</译文>

逐句做：
1. 数句子：源文 N 句，译文 M 句，不等就找漏句/合并。
2. 信息颗粒计数：每句列出主体/客体/动作/限定词/数量/时间/情态/否定，源译各数一遍，不等就停。
3. 五类检查：方向（谁→谁）/ 限定词 / 确定性等级 / 功能性句子是否还起原作用 / 标题定性。
4. 加戏：译文里有源文没有的信息点吗？
5. 过度润色：语义等级变了吗（尝试→成功、部分→全面）？
6. 数字、日期、货币、单位、URL：与源文逐个对照（脚本已扫过一遍，这里复核语境：¥ 指哪种货币？万/億换算对不对？）
7. 术语：命中条目用法是否一致。

规则：
- 只报有源文依据的问题；语感问题不在本遍范围（单语遍负责）。
- 每条给句级位置。
- 不确定的报「不确定」。
- 不要改写全段。

输出（严格按此格式）：
段号: {{段号}}
发现数: N
句数: 源 N / 译 M
---
B-01 【{{段号}} / 第 k 句】 类别：<方向|限定词|确定性|功能性|标题|漏句|加戏|过度润色|数字符号|术语>  确定度：<高|中|低>
- 源文：
- 译文：
- 问题：
- 建议：
...
```

## 4. 模板 C：怀疑论者复核

```
你是怀疑论者。别人审出了一批"错误"，你的工作是把误判挑出来，**不负责通过整份材料**。

语对：{{src}} → {{tgt}}；场景：{{场景一句话}}；材料类型：{{材料类型}}
先读：{{skill_dir}}/references/pairs/{{src}}-{{tgt}}.md、{{skill_dir}}/references/locales/{{locale}}.md、{{skill_dir}}/references/diagnostics.md 第 9.11 节（不该误杀的例子）
项目决定（空格、长音、术语等策略）：{{decisions 摘要}}

待复核清单（只含 critical / major）：
{{清单}}

对每条做三件事：
1. 反问：源文真的是这个意思吗？译文真的没表达出来吗？有没有语对包/locale 包/项目决定能解释现有写法？
2. 改写测试：按"推荐"改法把那一句改一遍。改后没有明显更好 → 降为 neutral。
3. 裁定：维持 / 降级为 <级别> / 驳回。**不确定就降一级**。每条一句理由。

输出（严格按此格式）：
复核数: N
---
F-xxx 裁定：<维持|降级为 major|降级为 minor|降级为 neutral|驳回>
- 理由：
- 改写测试：<明显更好|差不多|更差>
...
```

## 5. 模板 D：分段生成（translate 入口）

```
你在把一份 {{材料类型}} 从 {{src}} 本地化为 {{tgt}}（locale {{locale}}）。不是翻译，是**用目标语重新写一遍**。

场景：{{场景一句话}}
本次捷径（最要防的失败模式）：{{捷径描述}}
先读：
- {{skill_dir}}/references/pairs/{{src}}-{{tgt}}.md
- {{skill_dir}}/references/locales/{{locale}}.md
- 项目样式表：{{style-sheet 路径}}
- 目标语同类材料样本（如有）：{{样本路径}}。对照样本的句式、语体、段落长度、外来语比例。
本段命中的术语（必须用）：
{{glossary 命中条目}}
待确认清单里与本段相关的条目（按标注处理，不要自行决定）：
{{open-questions 命中}}

本段（{{段号}}）源文：
<源文>
{{源文段}}
</源文>

每句走三步：
① 意图抽出：这句到底想说什么？（脱离字面，写一行）
② 场景重建：目标市场的人在这个场景会怎么写？（不是"怎么译"）
③ 语感打磨：语体、长度、与样式表一致
每选一个词自问：我选它是因为源语也是这个形式，还是这类材料就这么写？前者就换。

规则：
- 读不出原意的地方**不猜**：在译文里用「【推测：…】」标出，并在输出末尾列进"新增待确认"。
- 数字、日期、货币、单位、URL、法人后缀、代码：按样式表处理，不确定的保留原文并标注。
- 不要加源文没有的信息，不要删限定词，不要把不确定说成确定。
- 有版式约束时（{{约束}}）：先找更短的原生说法，再考虑其他。

输出（严格按此格式）：
段号: {{段号}}
---
<译文>
{{译文段}}
</译文>
（**译文块里只放能直接上线的文字**。占位、方案对比、处理说明一律放到下面的两张表里，不要混进译文。）
---
新增术语（源语词 | 目标语词 | 理由 | 否决项）：
...
新增待确认（位置 | 现状 | 可能的解释 A/B | 影响范围）：
...
```

## 6. 模板 E：adapt 受控重构生成

```
你在执行一份已获作者授权的 adapt 任务，不是普通 translate。先完整读取：
- {{source path}}
- {{authorization path}}
- {{structure-options path}}
- {{fact-ledger path}}
- {{market-conventions path}}
- {{glossary path}}
- {{style-sheet path}}
- {{decisions path}}

只允许执行授权表中已批准的表达层动作。数字、日期、主体、对象、数量、时间、功能、价格、免费/付费条件、效果强度、法律含义、否定和限制永远不能改。
不要把源文矛盾自行修成事实；提出处理方案并留在 open-questions。

每个目标单元必须写入多对多映射：源单元集合 → 目标单元集合。每个映射记录保留的事实、授权编号、市场惯例依据和待作者批准项。一个源单元可拆成多个目标单元，多个源单元可合并成一个目标单元；不要用源译数量相等当覆盖证明。

目标稿每个单元前写锚点 `<!-- TGT-001 -->`（HTML 注释，渲染后不可见）。源文的 `<!-- SRC-00x -->` 锚点照抄不改。

**必须同时产出 adapt-map.md 的「事实落地表」，这是机检合同**：事实账本里每个非空颗粒一行，写清 FACT 编号、颗粒类别（与账本表头同名）、源文值（与账本一模一样）、落在哪个 TGT、以及**目标实现——你写进目标稿里的那个逐字串**。脚本会在那个单元里原样查找这个串，找不到就判这个颗粒在重构中丢了。合并两句时最容易丢的是否定、条件和主体，写落地表时逐个回去看一眼。

写完自己先跑，退出码不是 0 不要交：
python3 {{skill_dir}}/scripts/adapt_check.py map --source {{source path}} --ledger {{fact-ledger path}} --map {{adapt-map path}} --draft {{draft path}} --authorization {{authorization path}} --glossary {{glossary path}}

输出到 {{adapt output directory}}：
1. 可直接上线的目标语稿（带 TGT 锚点）
2. adapt-map.md（单元级映射表 + 事实落地表，都要逐条，不能只写摘要）
3. 新增待确认（未授权动作、源文矛盾、事实不明）
4. 新增术语和市场惯例（来源必须包含读者画像）
5. adapt_check.py map 的完整输出

完成前自己核：所有事实账本条目都有目标映射；所有结构变化都有 AUTH/DEC 编号；稿件没有内部说明、A/B 方案或推测占位混入正文。**脚本通过只说明形式合同成立，不说明语义没丢——你自己拿不准的地方照样要写进待确认。**
```

## 7. 模板 F：adapt 三方事实/所指审校

```
你是独立 adapt 审校者。不能读取生成上下文，只能读取：
- {{source path}}
- {{fact-ledger path}}
- {{adapt-map path}}
- {{adapt draft path}}
- {{authorization path}}
- {{approved structure path}}
- {{market-conventions path}}

**形式合同已由 `adapt_check.py map` 机检过**（映射覆盖、颗粒落地串是否逐字存在、主体定译、数字日期集合）。
**你的工作从机检停下的地方开始**：脚本只能证明「落地表声明的那个串确实在那个单元里」，
不能证明那个串**在语义上真的表达了那个颗粒**。所以对每个颗粒问的是：
把落地表上的源文值和目标实现并排看，目标语这句话读下来，**这个事实还在不在、强度有没有变、条件挂没挂在正确的对象上**。
典型漏法：否定改成了「原則として」这类软化表达；条件被挪到另一句管不着原来那个动作；
主体从「無料プランのユーザー」滑成泛指的「ユーザー」——这些机检全都放行。

不要因为源单元和目标单元数量不同就报漏译。必须沿着「源单元集合 → adapt-map → 目标单元集合」核对：
1. 主体、对象、动作、方向、数量、时间、情态、否定、条件、功能、价格、效果和法律承诺是否保留；
2. 是否出现未授权的结构/体裁动作；
3. 目标语是否符合已批准的目标市场惯例和材料角色；
4. 每个大改动是否有授权编号和证据；
5. 适配建议本身有没有改变所指或越过事实边界。

把发现分为：事实/所指越界、授权越界、映射缺口、市场惯例证据缺口、目标语自然度、结构适配、源文问题。事实/授权越界优先，不要被自然度掩盖。

输出：
| F-NN | 源单元集合 | 目标单元集合 | 类别 | 问题 | 严重度 | 依据 |
|---|---|---|---|---|---|---|

另外单列：
- 映射覆盖：源 <N> / 已映射 <M> / 未映射 <K>；目标 <N> / 有来源 <M> / 无来源 <K>
- 未审查单元
- 需要作者裁决的事实或授权问题
```
